# Taste
- Prefers the assistant to inspect the work directly rather than delegate repository investigation to subagents. Confidence: 0.85
- Writes requests in Chinese (Simplified) and expects replies in the same language. Confidence: 0.65
- Needs answers in plain language, not layer-by-layer API detail: when a reply is dense with internal names (methods, headers, protocol concepts) he replies "没听懂" and expects a rewrite that leads with the everyday behavior ("内容类型都能处理"), names the one real limitation in a single line, and ends with a one-sentence bottom line. Internal symbols are acceptable only as brief parentheticals to a concept already explained in ordinary words. Implies jargon-heavy "取决于哪一层" decompositions should be avoided unless the distinction is truly what he asked about. Confidence: 0.55
- Prefers terse, imperative instructions ("我希望你帮我把 X 改为 Y") with no background or rationale; expects the agent to act directly rather than ask for elaboration. Follow-ups are equally terse nudges ("继续", "继续补下一步测量") that assume the agent keeps executing the agreed plan without re-confirming each step. Confidence: 0.7
- For open-ended improvement work (e.g. "能不能进一步优化"), prefers a plan/options proposal first rather than immediate code edits; opens larger feature work with an explicit "开始规划" and expects a written plan (scope, wire/API design, acceptance thresholds, verification commands) before code. Confidence: 0.7
- Expects the agent to consult the web/external sources and ground recommendations in authoritative references when asked to propose a solution. Confidence: 0.7
- Wants design decisions validated against prior art before more code is written: asks for a survey of how mature/large projects (Go/JVM/nginx/Envoy/Tomcat/.NET-class systems) solve the same problem, and explicitly also for the research literature ("去网上搜搜论文, 优秀的实现啥的了解一下") — academic/industry papers (SEDA-style staging, NSDI-class backpressure work, RFC specs) alongside reference implementations — citing official docs/primary sources, with a verdict on how their own design compares (what matches convention, what is unusual) and which parts to copy. Confidence: 0.7
- Research is expected to end in adoption, not another round of discussion: after a prior-art survey, orders the consensus pattern copied directly into the codebase ("抄过来", i.e. land bounded queue + 503/Retry-After overload rejection like nginx/ThreadPoolExecutor) while keeping the already-agreed design (on-demand growth) intact. Confidence: 0.6
- Wants prior art reproduced faithfully, not reinterpreted: when the first pass picked only the "spirit" of the convention, restates it as "抄的一模一样" and expects the upstream mechanism landed as-is (bounded queue, reject-on-full, 503 + Retry-After, observable counters, defaults still derived rather than hardcoded) — a partial or watered-down adoption is treated as not having done the task. Confidence: 0.7
- Comfortable authorizing large, architecture-level changes (new concurrency models, new I/O backends, public-API additions such as a coroutine takeover path) rather than only low-risk micro-optimizations, provided the reasoning for each step is explained; justifies them with a plain statement of the real production target ("确实是要几千并发的", "我需要极致的性能") rather than a request for cautious, incremental rollout. Confidence: 0.7
- Sets performance as the overriding design goal rather than one concern among many ("我需要极致的性能", and again "不只是LLM, 我希望他能够在任何场景都做到极致性能"): expects architecture chosen for the performance ceiling (latency, per-request CPU/syscall, per-stream memory, throughput, zero-copy/zero-alloc hot paths, single-runtime fast paths) even at the cost of a rewrite, and wants the goal converted into hard numeric acceptance gates plus profiler/allocator/syscall measurements instead of qualitative claims. Confidence: 0.8
- Requires the performance goal to hold across every workload class, not just the current use case: when a design is scoped to one scenario (e.g. the LLM streaming gateway), pushes back that it must be extreme in all scenarios (SSE, unary, large bodies, tunnels) at once. Implies he rejects one-purpose supplemental code paths and fixed tuning constants in favor of a single shared fast path whose strategy adapts at runtime per request, and expects the claim backed by a benchmark matrix spanning those scenario classes. Confidence: 0.7
- Judges "optimization" work by measurable before/after results, so accepts baseline benchmarking, staged landing of changes, and full test regression as part of the task. Explicitly rejects prose-only conclusions ("给我数据, 不好空口说"): any claim about a gain must come with measured numbers from a real run, not reasoning or estimates. Confidence: 0.7
- When given benchmark results, expects the full detailed numbers (per-run figures, latencies, RSS, throughput tables) rather than summarized ranges or a narrative digest; asks again for "更详细的数据对比" when the summary is too compressed. The "对比" wording matters: wants an actual baseline-vs-new A/B (pre-change build run against the new one, interleaved on the same machine/compiler, per-run values and medians, noise flagged) rather than absolute numbers for the new version alone. Confidence: 0.7
- Expects every new benchmark to be placed side by side with the project's previously reported numbers: when a report only covers the new implementation, follows up with "跟原来的数据对比呢?" and expects the older published baselines (previous pump-pool / async / llm figures) re-run on the same machine and load client, normalized when loads differ (wall time ÷ stream duration, per-stream overhead), plus an explicit statement of where an old headline number is not directly comparable and which measurement is still missing. Regressions in the comparison (e.g. worse TTFT from buffering) must be stated plainly, not hidden behind the win. Confidence: 0.75
- With terse follow-ups like "提交并推送", wants the agent to go ahead and finish the VCS loop itself — stage the relevant files, write the commit, and push straight to the default branch (origin/main) — rather than stopping to propose a commit message or open a PR/branch for review; local tool artifacts (e.g. `.commandcode/`) are left untracked. Confidence: 0.6

Confidence: 0.55

Wants arbitrary ceilings treated as things to raise, with the break-even point measured. Confidence: 0.55
- When presented with multiple options or a research report, typically does not pick one explicitly: approves with a minimal token ("可以, 尝试一下", "抄过来") and defers to the agent's own recommendation, then expects the whole loop (implement, instrument/benchmark, document, run the full test suite) delivered without intermediate check-ins — a bare "继续补下一步测量" is enough authorization to build the missing benchmark mode, run it locally and in the constrained container, write the numbers into the docs, and re-run the suite before reporting.
